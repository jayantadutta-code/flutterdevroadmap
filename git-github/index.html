Version Control Fundamentals

What is Git?

Git is a distributed version control system created by Linus Torvalds in 2005 while developing the Linux kernel. It tracks file changes over time using immutable cryptographic SHA-1 hashes, acting as a project timeline where saved checkpoints are called commits.

Before Git vs With Git

Before Git, developers created manual zip backups (e.g. project_v1.zip, project_final2.zip). Git replaces this chaos with single-command snapshots that can be compared, audited, or reverted anytime without losing work.

The 4 Core Storage Areas

1. Working Dir Files on disk
add
2. Staging Index Ready for commit
commit
3. Local Repo .git history
push
4. Remote Repo GitHub cloud

Understanding Version Control Systems

Centralized vs Distributed VCS

Centralized VCS (SVN, CVS): A single central server holds official project history. If the server goes down, collaboration and commits stop.
Distributed VCS (Git, Mercurial): Every developer holds a full copy of the entire repository history on their local machine, enabling instant offline work.

Feature Centralized VCS (SVN) Distributed VCS (Git)
Full History Copy On server only On every local machine
Offline Commits Impossible Full offline support
Backup Reliability Single point of failure Multiple complete redundant backups
Branching Speed Slow server operation Instant local pointer shift

Git vs GitHub & Hosting Platforms

Clarifying Git vs GitHub

Git is the local command-line version control tool installed on your computer.
GitHub is a web cloud hosting service for Git repositories that adds social collaboration tools like Pull Requests, Issue tracking, and Code Reviews.

Property Git GitHub
What it is Version Control Tool Cloud Web Hosting Service
Runs on Your local computer Cloud servers
Internet Needed No (for local commits) Yes (to push/pull/sync)
Core Function Tracks file diffs & commits Host repos, PRs, Issues & Actions

GitHub Alternatives

Other cloud hosting services that work natively with Git include GitLab, Bitbucket, and Codeberg.

How Git Works & The 4-Area Cycle

The 4-Step Git Workflow Cycle

1. Edit: Modify files in your Working Directory.
2. Stage: Run git add . to queue modified files into the Staging Index.
3. Commit: Run git commit -m "msg" to save a permanent snapshot.
4. Push: Run git push origin main to upload commits to GitHub.

Understanding Commit Snapshots

Unlike version control systems that store file diff lists, Git records an immutable snapshot of your entire repository state at every commit point. You can view all snapshots using git log --oneline Page 20.

Configuring Git & Author Identity

1. Configure Git Author Identity

These settings tell Git who is making commits.

Set Your Name:
git config --global user.name "Your Name"
git config --local user.name "Your Name"
Set Your Email:
git config --global user.email "you@example.com"
git config --local user.email "you@example.com"
--local → Applies only to the current repository.
--global → Applies to all repositories.
Verify:
git config --global user.name
git config --local user.name
git config --global user.email
git config --local user.email
git config --list

2. Set Default Branch Name

Instead of using master, Git can create repositories with main.

git config --global init.defaultBranch main
Verify:
git config --global init.defaultBranch

3. Configure Default Editor

A. Android Studio as Git Editor

Windows
Locate your Android Studio installation. Usually:
C:\Program Files\Android\Android Studio\bin\studio64.exe
Run:

git config --global core.editor "'C:/Program Files/Android/Android Studio/bin/studio64.exe' --wait"
Verify: git config --global core.editor

macOS
Android Studio application path:
/Applications/Android Studio.app
Use:

git config --global core.editor "open -W -a 'Android Studio'"
Verify: git config --global core.editor
B. Visual Studio Code as Git Editor

Before configuring Git, install the Shell Command in VS Code:
Open VS Code → Command Palette → Search: Shell Command: Install 'code' command in PATH

Windows

git config --global core.editor "code --wait"

macOS

git config --global core.editor "code --wait"
Verify: git config --global core.editor

4. View All Global Git Configuration

git config --global --list

Example Output:

user.name=John Smith
user.email=john@gmail.com
init.defaultBranch=main
core.editor=code --wait

5. Find Where Git Stores Global Configuration

Windows: C:\Users\<username>\.gitconfig
macOS: ~/.gitconfig

Open it: cat ~/.gitconfig

6. Change Existing Configuration

Change your name:
git config --global user.name "New Name"
Change your email:
git config --global user.email "new@email.com"
Change editor:
git config --global core.editor "code --wait"
or
git config --global core.editor "open -W -a 'Android Studio'"

7. Remove a Configuration

Remove editor:
git config --global --unset core.editor
Remove user name:
git config --global --unset user.name
Remove email:
git config --global --unset user.email

8. Key Differences

Command Purpose Scope
git config --global init.defaultBranch main Sets the default branch name for new repositories created with git init. All future repos
git branch -M main Renames the current branch to main. Current repo only
When to Use Each:
  • Use git config --global init.defaultBranch main once when setting up Git on a new computer.
  • Use git branch -M main when you want to rename an existing repository's branch (for example, from master to main).

9. Enable Colored Git Output

git config --global color.ui auto
What it does:

This tells Git to automatically use colored output when the terminal supports it:

green → added lines red → deleted lines yellow → warnings blue → branch info

This makes commands like git status, git diff, and git log much easier to read.

Configuration Level:
--global → Applies to all repositories for the current user.

Equivalent entry in your .gitconfig:

[color]
    ui = auto
Verify:
git config --global color.ui
Output: auto

Your First Git Repository

Command Purpose (What to Do)
mkdir "folderName"
Create a new folder (directory).
cd folderName
Move into the specified folder.
git init
Initialize a Git repository in the current directory.
git init "folderName"
cd "folderName"
Create a Git repository inside the specified folder, then move into that folder.
echo "# This is first line." > README.md
Create a new README.md file and write the first line. If the file already exists, its previous contents will be overwritten.
git status
Display the current status of the working directory and staging area.
git status -s
Display the repository status in a short (compact) format.
git add .
Stage all new, modified, and deleted files for the next commit.
git add "fileName"
Stage only the specified file for the next commit.
git rm --cached "fileName"
Remove the specified file from the staging area without deleting it from your local computer.
echo "# This is another file and first line." > hello.txt
Create a new hello.txt file and write its first line.
cat hello.txt
Display the contents of hello.txt in the terminal.
git add README.md hello.txt
Stage multiple specified files for the next commit.
git status -s
Status Codes: ?? = Untracked file, A = Added (Staged), M = Modified, No output = Working tree is clean (all changes have been committed).
git commit -m "message"
Save all staged changes as a new commit with the specified commit message.
git log
View the complete commit history with detailed information.
git log --oneline
View the commit history in a compact one-line format.
echo "# This is second line." >> README.md
Append a new line to the end of README.md without removing existing content.
echo "# This is second line." > README.md
Replace the entire contents of README.md with the new line.
git restore README.md
Discard all uncommitted changes in README.md and restore it to the last committed version.
echo "# Second line" >> hello.txt
Append a second line to the end of hello.txt.
echo "This is new line replace old one" > README.md
Replace all existing content in README.md with the new text.
git commit -am "Second commit"
Automatically stage all modified tracked files and create a new commit in a single command. (Does not stage new/untracked files.)
git commit -a
Automatically stage all modified tracked files and open the text editor for writing a message. If the Vim editor opens: press i to start writing, after write is complete press Esc, type :wq, then press Enter to save and exit.
git commit --amend
Modify the most recent commit (change its message and/or include additional staged changes). If the Vim editor opens: press i to enter Insert mode, edit the message, press Esc, type :wq, then press Enter to save and exit.

Your First Project Walkthrough

Complete Project Step-by-Step

  1. mkdir hello-git && cd hello-git
  2. git init
  3. echo "# Hello Git" > README.md
  4. git add README.md
  5. git commit -m "initial commit"

Commit Best Practices

  • Commit whenever a logical unit of work is done.
  • Write present-tense messages (e.g. add login form not added login form).
  • Keep commits atomic and focused on single feature ideas.

Ignoring Files (.gitignore & .gitkeep)

Why Use .gitignore?

Secrets, environment API keys (.env), build outputs (dist/), OS junk (.DS_Store), and heavy node_modules/ should never be committed into Git history.

Pattern Rule Effect
.env Ignores environment file containing secrets
node_modules/ Ignores entire dependency folder recursively
*.log Ignores all log files matching wildcard
!important.log Negation rule: explicitly tracks this log file
git rm --cached <file> Stop tracking file without deleting locally

Working Alone with Git & Rollbacks

Daily Solo Developer Workflow

Morning: git status & git pull origin main
During Day: git add . & git commit -m "msg" (frequently)
End of Day: git push origin main

Rollback Action Command
Discard working edits git restore <file>
Discard all working edits git restore .
Undo commit (keep staged) git reset --soft HEAD~1

Team Collaboration Rules

Team Action Command

Merging Branches & Deletion

Fast-Forward vs Merge Commit

Fast-Forward: Occurs when target branch has no new commits; Git simply moves branch pointer forward.
Merge Commit: Occurs when both branches diverged; Git generates a new merge commit object joining both histories.

Command Purpose
git merge <branch> Merge branch into active
git branch -d <branch> Safely delete local branch
git push origin --delete <branch> Delete remote branch on GitHub

Git Stash (Temporary Parking)

Why Use Git Stash?

Stash saves your uncommitted working directory changes temporarily so you can switch tasks or fix urgent hotfixes without committing unfinished half-done code.

Stash Action Command
Save stash with note git stash push -m "..."
List all stashes git stash list
Restore & drop stash git stash pop
Apply stash (keep entry) git stash apply
Clear all stashes git stash clear

Merge Conflicts & Resolution

Conflict Markers

<<<<<<< HEAD
your local version
=======
their incoming version
>>>>>>> feature/search

Git pauses merges when overlapping lines are edited differently. Edit the file, remove conflict markers, then stage and commit.

Resolution Action Command
Inspect resolved diff git diff --staged
Abort conflicting merge git merge --abort

Undoing Mistakes (Reset vs Revert)

Reset Levels & Revert Safety

Reset --soft: Undoes commit (keeps code staged).
Reset --mixed: Undoes commit & staging (keeps code edited).
Reset --hard: Permanently destroys uncommitted edits!
Git Revert: Safe for pushed commits; creates a new commit reversing changes without rewriting history.

Undo Command Safety Level
git revert HEAD Safe Undo
git reset --hard HEAD~1 Hard Reset
git reflog Safety Net

Git Rebase & Linear History

Rebase vs Merge

Instead of creating a merge commit, rebase replays your feature branch commits on top of target branch HEAD, creating a clean linear project history.

Property Git Merge Git Rebase
History Preserves branch fork Linear & clean
Merge Commit Yes No
Public Branches Safe Never rebase public shared branches
Command Purpose
git rebase origin/main Rebase feature branch onto remote main
git push --force-with-lease Safely force push rebased branch

Git Tags & Release Milestones

Lightweight vs Annotated Tags

Lightweight Tag: Simple bookmark pointer to a commit hash.
Annotated Tag: Full release milestone object containing tagger name, date, message, and GPG signature.

Tag Command Purpose
git tag -a v1.0.0 -m "..." Create annotated release tag
git push origin --tags Upload release tags to GitHub

GitHub Essentials & Fetch vs Pull

Fetch vs Pull

git fetch: Downloads remote updates safely to remote-tracking branches (e.g. origin/main) without touching local working files.
git pull: Shortcut command combining git fetch followed immediately by git merge.

Command Action
git remote add origin <url> Link local repo to GitHub endpoint
git push -u origin main Initial push & set upstream tracking

Cloning Projects (HTTPS vs SSH)

HTTPS vs SSH Protocols

HTTPS: Easiest to start; requires Personal Access Token (PAT) when pushing.
SSH: Recommended for daily use; uses SSH key pair for seamless passwordless authentication.

Command Method
git clone https://... HTTPS Clone
git clone git@... SSH Clone

GitHub Desktop & Forking Workflow

What is Forking? (Fork vs Clone)

Fork: Creates your personal copy of someone else's repository under your GitHub account, letting you experiment and submit Pull Requests freely.
Clone: Downloads a repository copy to your local computer.

Action Fork Clone
Location Created on GitHub cloud Created on local disk
Ownership You own the forked repo copy Identical local copy
Purpose Open-source contribution via PRs Daily local development

Modern Git Workflow in the AI Era

Git While Vibe Coding

AI code generation is fast, but can introduce bugs. Use Git as your safety harness:
1. Commit BEFORE AI edits: git commit -m "working state"
2. Audit AI changes: git diff --stat
3. Rollback bad AI output: git restore .

Git Best Practices & Secret Security

Never Commit Secrets

Passwords, API keys, and .env files must never enter Git history.
If a secret is accidentally staged: run git rm --cached .env, add .env to .gitignore, and rotate the secret key immediately!
